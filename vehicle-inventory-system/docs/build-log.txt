VEHICLE INVENTORY SYSTEM — BUILD, ITERATION & TEST LOG
=======================================================
Portfolio/demo build. Not a record of a specific past client engagement — see
README.md and docs/case-study.html for that context.


1. ORIGINAL BRIEF (as provided)
--------------------------------
The application will primarily be a backend system with a minimal admin UI.
The focus is on clean architecture, maintainable code, and a well-designed
REST API.

Tech Stack
- Java 17+
- Spring Boot
- Spring Security
- JPA / Hibernate
- Supabase
- Maven or Gradle

Project Features
The system should allow management of cars with information such as:
- Brand
- Model
- Year
- Engine
- VIN
- Mileage
- Purchase Price
- Selling Price
- Current Status (Available, Reserved, Sold, In Transit, etc.)
- Vehicle Condition
- Notes
- Multiple Photos
- Date Added
- Last Updated

Frontend
Only a very simple admin interface is needed to:
- Add vehicles
- Edit vehicles
- Upload photos
- View vehicle list
- Filter/search vehicles
- View dashboard

"The UI doesn't need to be fancy. Functionality is much more important than
design."

5. TEST ITERATIONS
--------------------
Four real issues were caught and fixed during this build, in the order found.
Each is a genuine bug that would have shipped if the code had only been
written and never actually run.

5.1  Integration tests silently never ran
    Symptom : `mvn test` reported BUILD SUCCESS with only 6 tests executed
              (InventoryApplicationTests + VehicleServiceTest). The two
              @SpringBootTest/MockMvc classes were named VehicleControllerIT
              and AuthControllerIT.
    Cause   : Maven Surefire's default include pattern only picks up
              *Test.java (and a few similar patterns) — *IT.java is the
              Failsafe convention, bound to `mvn verify`, and no Failsafe
              plugin was configured in this pom.xml. The IT classes were
              being compiled but never executed by `mvn test`.
    Fix     : Renamed VehicleControllerIT.java -> VehicleControllerTest.java
              and AuthControllerIT.java -> AuthControllerTest.java (class
              declarations updated to match) so `mvn test` alone runs the
              whole suite with no extra plugin wiring needed.

5.2  H2 schema creation failing on the `vehicles` table
    Symptom : Buried in the same test run's log (not a build failure, just a
              WARN — easy to miss): Hibernate's auto-DDL against the H2
              dev/test database threw a syntax error creating the `vehicles`
              table, then a second error trying to add the vehicle_photos ->
              vehicles foreign key ("Table VEHICLES not found").
    Cause   : YEAR is a reserved word in H2's grammar. The entity's `year`
              field was mapping to an unquoted `year` column, which H2's
              parser rejected outright — so the whole table silently failed
              to exist. (PostgreSQL, the real target, does not reserve YEAR
              as an identifier, so this would NOT have surfaced against a
              real Supabase database — only against H2, and only because
              the table failed to create, not because of a runtime query.)
    Fix     : Vehicle.java's `year` field now maps to `@Column(name =
              "model_year")` — the Java/JSON field name stays `year`
              (that's what the API and callers should see); only the SQL
              column name changed. Applied the same column name in
              db/migration/V1__init_schema.sql so dev (H2) and prod
              (Supabase Postgres via Flyway) stay in sync.

5.3  Anonymous requests returned 403 instead of 401
    Symptom : VehicleControllerTest.anonymousRequestIsRejectedWithUnauthorized
              failed: "Status expected:<401> but was:<403>".
    Cause   : No formLogin()/httpBasic() is configured (this API is pure
              JWT), so Spring Security had no AuthenticationEntryPoint wired
              up and fell back to rejecting unauthenticated requests with a
              bare 403 rather than a 401.
    Fix     : SecurityConfig now sets an explicit
              `.exceptionHandling(ex -> ex.authenticationEntryPoint(...))`
              that returns 401 for any request that reaches the filter
              chain unauthenticated — the correct, REST-conventional status
              for "you're not logged in" vs. 403's "you're logged in but not
              allowed."

    Result after 5.1-5.3:
    $ mvn test
    Tests run: 15, Failures: 0, Errors: 0, Skipped: 0
    BUILD SUCCESS
      - InventoryApplicationTests ..... 1 test  (context loads)
      - VehicleServiceTest ............ 5 tests (Mockito unit tests)
      - AuthControllerTest ............ 3 tests (login, bad password, token
                                                  grants access downstream)
      - VehicleControllerTest ......... 6 tests (auth required, CRUD,
                                                  duplicate VIN -> 409,
                                                  validation -> 400 with
                                                  field errors, search
                                                  filters, delete cascades
                                                  to photos)

5.4  `mvn spring-boot:run` crashed on startup: "Cannot load driver class:
     org.h2.Driver"
    Symptom : `mvn test` was fully green, but actually running the app (dev
              profile, H2) failed immediately with a HikariDataSource /
              driver-loading exception.
    Cause   : The h2 dependency was declared with `<scope>test</scope>`, so
              it's on the test classpath but NOT on the classpath for an
              actual `spring-boot:run` execution. Tests alone never caught
              this because tests only ever exercised the Spring context via
              the test classpath.
    Fix     : Changed h2's scope from `test` to `runtime` in pom.xml — the
              whole point of the H2-backed `dev` profile is letting
              `mvn spring-boot:run` work with zero external database setup,
              so H2 has to be present at actual runtime, not just in tests.

7. COMMAND REFERENCE
-----------------------
Run the test suite:
    mvn test

Run locally against H2 (no Supabase project needed for this):
    export APP_ADMIN_SEED_PASSWORD=ChangeMe123!
    mvn spring-boot:run
    # -> http://localhost:8080, sign in with admin / ChangeMe123!

Run against real Supabase (production profile):
    SPRING_PROFILES_ACTIVE=prod \
    SUPABASE_DB_URL=... SUPABASE_DB_USERNAME=... SUPABASE_DB_PASSWORD=... \
    SUPABASE_URL=... SUPABASE_SERVICE_ROLE_KEY=... \
    APP_JWT_SECRET=... APP_ADMIN_SEED_PASSWORD=... \
    mvn spring-boot:run

Package a runnable jar:
    mvn clean package
    java -jar target/vehicle-inventory-system.jar
